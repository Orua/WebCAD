# WebCAD 圆角／圆润升级：总执行与验收指令

继续当前工作区中的通用圆角／圆润工具升级。

本指令调整之前的执行顺序与停止规则：
不再以 T2 作为所有后续任务的串行门槛，
不再在每完成一个探针或阶段记录后结束任务并等待我重新下指令。

保留原升级方案的几何要求、功能范围、兼容要求和测试标准。
本任务仍然是完成正式通用工具，不是研究某个产品，
也不是只输出问题定位、日志和下一步建议。

一、保留现有成果，明确当前阻塞

根据已有实测记录：
- T0/T1 已有通过证据，保留并回归，不从头重写。
- T2 的自定义规律在 Simulate 后可注入，
  但 Build 后被默认规律覆盖。
- 这证明当前注入路线不能满足要求，
  不证明全部变 R 无法实现，更不证明 T3/T4 无法实施。
- 已有截面验证器是辅助能力，不算 T3/T4 构造算法完成。

读取已有阶段记录、源码、探针和结果文件。
不重复完整的失败参数枚举，不重新制作内容相同的诊断报告。

先记录当前 HEAD、工作区差异、依赖和实际 WASM 哈希，
按 AGENTS.md 备份，保留未提交改动。

二、执行方式：按依赖推进，不因一个分项卡住停掉全部

建立任务清单，列出每个必做能力的：
依赖、当前实现、待做代码、对应验收案例、状态和阻塞原因。

接下来按以下原则推进：

1. 立即实施不依赖 T2 的 T3：
   先完成两平面直边的解析恒 R 构造，
   再完成原方案规定的解析曲边构造。
   实现不能只停留在 agent/temp，必须接入正式 rounding 工具。

2. 接着实施不依赖严格线性 law 的 T4：
   两平面对称／非对称宽圆润，
   再推进规则曲边、四边界约束补面和局部替面。

3. 端点、整件范围、历史、预览、UI/API和文件闭环，
   哪部分依赖已经满足，就完成哪部分。
   不必等所有几何模式成功后才开始集成。

4. T2 保留为必须完成的独立工作项：
   从“继续试接口调用”转入
   “自定义规律的持久化与重建机制修复，
   或能满足同一规律要求的独立构造路线”。

5. T3/T4 成功不能代替 T2 成功。
   调整实施顺序不等于删除严格变 R要求。

不要求多代理或多个线程同时修改仓库。
一个主执行者按依赖顺序实施即可，
避免多个代理同时改同一模块。

三、允许进行隔离的内核修补，不允许破坏现有基线

允许在项目隔离目录或候选构建中：
- 获取与构建来源相符的源码；
- 编写有针对性的 C++／绑定补丁；
- 编译候选 WASM；
- 在测试页面和真实内核测试中加载候选版本。

原 WASM 保留为只读基线，不覆盖唯一副本。
候选版本必须有独立标识、源码提交、补丁、构建脚本和哈希。

候选通过相关回归后，允许修改本地开发构建的引用，
并保留一键回退到原基线的方法。
这不授权推送、线上部署或覆盖生产资源。

禁止：
- 无证据地全量升级所有依赖；
- 只修改 node_modules 而没有可复现补丁；
- 为保住临时 law 而全局删除 Reset；
- 保留过期轮廓、旧模拟面或失效的内核缓存；
- 用构建来源标签冒充 WASM 自带的确切版本证明；
- 将不同候选内核上的通过结果拼成“同一交付版本全部通过”。

若需要安装系统级软件、购买服务、改变系统配置或上传客户数据，
先记录明确需求；这些操作不在本指令的默认授权范围。
先继续其他能够执行的任务，不因这一项立即停止全部开发。

四、T2 修复的目标是“请求能持久重建”，不是临时读回成功

研究并实现以下生命周期，具体代码方案以源码和测试为依据：

用户规律定义
→ 按源边链及方向保存
→ 构建重置
→ 根据本次实际轮廓重新映射规律
→ 几何求解
→ 最终结果验证
→ 历史改参后再次重建

用户要求的规律与求解器派生缓存要分开保存。
不能只把 law 塞进 Simulate 后的临时列表。

必须处理：
- 单边和整条链的参数映射；
- 边链方向；
- 多站点；
- 轮廓分段；
- 端部外延；
- 编辑、删除或替换半径定义后的失效规则；
- 重复构建不能回到旧规律。

这不是要求通过删除 Reset 修复。
应保留必要的缓存清理，再从持久请求重新生成正确规律。

若当前锁定源码的自定义 law 路线确需修补，
在候选内核实现并验证，不继续盲试已失败的调用顺序。

另一条构造路线只有在同样满足请求规律、
支撑接合、作用范围和实体要求时，才能替代。
普通放样、默认平滑 law、加密站点都不能自动算等价。

五、几何总验收标准

所有正向功能必须运行真实 WASM，
使用与最终交付版本一致的正式算法。

每项结果至少同时满足：

A. 实体正确
- BRep 有效；
- 单实体模式得到合法闭合单实体；
- 壳和面方向正确；
- 无额外碎体、重叠面或意外空洞；
- 原有合法内腔保留。
不要把 shellCount 必须等于 1 当作通用要求。

B. 请求正确
- 恒 R符合用户指定半径；
- 变 R符合指定站点位置和插值方式；
- 宽圆润符合两侧宽度和接合轨线定义；
- 不静默改小 R、改插值、改宽度或改端点要求。

C. 接缝及端点正确
- 圆角带与支撑面满足本模式的接合要求；
- 自然终止允许已声明的正常端部轮廓；
- smooth-region 必须检查两端和交汇区域，
  不能放行新增台阶或短锐边；
- 有拓扑分界线不等于几何不光顺，不能为了抹线破坏模型。

D. 作用范围正确
- 真正处理了全部已确认目标；
- 相切传播没有越过授权范围；
- 排除区域没有被加工；
- 无关孔、字、邻面和其他实体未被意外改变。

E. 材料正确
- 凸角、凹角和混合区域分别核对；
- 不要求所有圆角净体积都下降；
- 不以整个零件的大体积百分比掩盖局部材料错误；
- 不强求所有圆角操作前后包围盒完全一致。

F. 数值证据正确
- 延续已固定的测试容差，失败后不得放宽；
- 高精度合成样例的长度／半径核对采用既定门槛，
  缺少明确值时先固定为 1e-5 mm，
  相切夹角门槛沿用 0.1°；
- 这些是本项目测试门槛，不是行业标准，
  不直接套给精度不足的导入模型；
- 采样结果须报告覆盖范围，不能声称是全局数学证明。

半径检查应使用生成过渡面的正确几何定义或正确截面。
不能对任意方向截面强行拟圆，
也不能要求圆角面所有主曲率都等于 1/R。

六、按原验收矩阵逐项关闭，不准用测试数量代替功能完成

读取原 rounding-acceptance-matrix.json。
保留全部原案例 ID、期望类型及断言。

该矩阵包含：
- 24 项 must_succeed；
- 13 项 must_reject_unchanged；
- 9 项 must_preserve_or_match。

对每项记录实际结果，不预填 passed。

must_succeed：
必须产生符合全部断言的正式几何结果。
返回“不支持”、提前拒绝、改小 R、只构建一个临时曲面，
均不能算通过。

must_reject_unchanged：
必须在该案例要验证的环节正确拒绝，
并确认模型、历史和 revision 没有部分提交。

例如：
用于验证“过大 R发生几何冲突”的案例，
要先保证选区、引用和传播授权有效。
若提前因 SCOPE_EXPANSION_REQUIRED 被拒绝，
只能证明范围保护有效，不能算已验证过大 R碰撞。

must_preserve_or_match：
必须实测兼容、等价或使用链路一致性。
不能只比较保存的参数，也不能只比较体积。

新增几何族要包含原方案要求的尺度及刚体变换版本。
不硬编码产品编号、固定边号、特殊尺寸或固定世界方向。

若发现测试本身存在可证明的规范错误：
保留原始失败证据，单独提出并说明规范修订，
不能悄悄改断言让实现通过。
必做能力被削减，需要我明确确认，不能自行决定。

七、正式工具的完成标准

每种必做模式都必须：
- 从正式界面入口使用；
- 通过公开页面 API使用；
- 预览和提交使用同一套构造；
- 参数可读回且含实际生效值；
- 修改原特征时从其上游输入重建；
- 撤销／重做正确；
- 保存工程后重新打开可重建；
- STEP 导出后在新会话重新导入并核对几何；
- 人工与 API结果在约定容差内等价。

一次多边／多链操作只能原子提交。
某个必需部分失败，不得保留其他部分的半成品提交。

取消、超时和旧预览要真实验收：
- 旧结果不能覆盖新参数；
- 不只是界面显示“已取消”，计算仍永久占用 Worker；
- 能停止试算或恢复 Worker；
- 原工程及未提交输入保持合理状态。

旧 fillet、smoothTransition、autoRound 和 chamfer
不得被新模式偷偷改变语义。

文档、工具卡、schema、UI/API coverage 与正式实现同步，
不能先在文档中宣称尚未通过的能力。

八、正确处理旧测试失败，不无限重复记账

对“期待错误文本包含减小数值”的既有失败：

先检查当前正式错误契约。
- 若错误信息仍属于承诺内容，修实现。
- 若旧断言已经过时，保留依据，
  改为检查当前规定的错误码、参数路径、
  请求未被改变及工程回滚等稳定语义。

不能仅删除测试，也不能把真实功能回退解释成文案问题。
相关测试修正后重跑，不在每份报告里重复挂同一个已知问题。

九、停止规则：停止的是无效路线，不是整个项目

同一失败机制连续两次没有新增证据：
- 关闭该实验路线；
- 记录输入、错误、已排除原因及最小复现；
- 不再重复相同调用和参数域枚举；
- 转入有依据的另一条路线，
  或实施其他不受阻塞的任务。

没有新证据，不允许再开启相同实验。
有新的源码修补、调用生命周期变化或构造方法，
才算不同路线。

“底层接口有缺陷”“这次 Build失败”
不能作为整个项目结束的充分理由。

不要求无限试错，也不要求虚构成功。
已选的合理路线仍无法通过时，标记该分项 blocked/failed，
继续完成所有还能执行的独立工作。

十、整个任务只能以下列状态收尾

状态一：DONE——完整完成
必须满足：
- 原方案全部必做能力已实现；
- 原验收矩阵全部通过；
- 正式 UI/API/历史/文件闭环通过；
- 相关回归和 build/release gate通过；
- 没有 required 项为 failed、blocked、not_run或 skipped。

只有这时才能说“圆角／圆润升级完成”。

状态二：BLOCKED_WITH_DELIVERY——交付部分成果，整体未完成
必须同时满足：
- 所有不受阻塞的必做任务均已实施并验收；
- 剩余每项都有可复现证据和具体阻碍；
- 说明已经采用或排除的合理路线及依据；
- 说明解除阻碍所需的最小条件；
- 正式代码、测试、已完成工具和文档已经实际交付；
- 没有把“尚未开始”包装成“被 T2阻塞”。

可接受的阻碍包括经过核实的构建环境缺失、
所需权限或资源不可用，以及已实施路线仍存在明确算法缺陷。
只说“很复杂”“需要更多研究”不够。

BLOCKED_WITH_DELIVERY 不是成功，不得把 blocked记为 passed。

状态三：CHECKPOINT——会话或执行环境被迫中断
只有实际执行限制导致无法继续时使用。
保存源码、差异、测试结果和精确续接入口，
明确标记整体未完成。
不能把普通阶段结束当作这种限制，
也不能承诺在后台继续工作。
