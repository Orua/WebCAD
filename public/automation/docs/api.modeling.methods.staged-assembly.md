# api.modeling.methods.staged-assembly

# 分批建模与交付

**多配件建模与分批交付**
>
用户要求建立多个配件、装配体或复杂产品时，先提交可核对的建模规划，再进入建模轮次。已有明确且获用户确认的规划应直接沿用；单个简单件不强制增加规划确认。
>
**规划轮次：**读取足以判断结构与关键尺寸的来源，分清组件种类、各类数量、独立活动件及制造件。用简表列出配件名称/编号、数量、来源与关键尺寸、相互连接与方位、计划批次和本批验收点。区分已知、可推导、用户允许假设和未解决项。确定统一基准、轴向、装配方向；未知项只阻塞受影响的配件。先形成简短规划，不为未开始的细节遍历工具、批量裁图或生成全套脚本。
>
将规划作为本轮正式回复提交，明确首批将完成哪一个或哪几个配件、暂不包含哪些细节及需要用户决定的事项，并等待确认。保存规划时核对文件写入回执；文件保存失败仍可在回复中交付完整规划，但不能声称已写入。规划确认前不创建、删除或重排几何；不把内部思考或一句“接下来开始”算成规划交付。
>
**执行轮次：**确认后只执行当前约定批次，通常是一个配件，或几个依赖简单、能一起核对的小配件；重复件先完成一件并确认尺寸/姿态，再按已确认的数量和间距复制。首批优先形成有用且可验收的工程成果。未经用户同意，不为赶进度用粗略模板替代要求中的真实轮廓、截面、孔槽、活动结构或文字。
>
工具只读取当前批次所需完整卡。复用已验证来源、静态知识、当前有效状态和成功回执；跨轮次从最新规划与工程状态续做，避免重新分析整张图。尺寸或方法已明确时，使用现有有界批处理；需要中间拓扑或用户判断的地方才拆开。遵守部分提交与原子事务各自的规则。
>
**批次交付：**至少报告本轮实际新增/修改的配件、工程提交状态与revision、关键尺寸/方位检查、缺失或尚未验证的细节、下一批内容。对本批做一次相关画面检查；已有充分的量测/回执不反复查询。截图失败不重复建模，说明视觉确认待补。只在宿主已确认暂存时报告恢复点；几何成功、画面确认、文件生成、写盘、附件交付分别表述。
>
正常批次结束后等待用户确认或“继续”。用户已明确授权按规划连续推进时，沿用该授权，每批仍回报实际成果；不因格式修正、只读检查或正常重连反复请求确认。用户改变尺寸、配件范围或方位时，只更新受影响规划和依赖部分。
>
**无进展与阻塞：**不能长时间只说“准备、分析、马上开始”。如果当前批次持续没有新增工程成果，先判断是缺来源、模型尚未形成方案、参数错误、页面连接阻塞，还是原作业仍在运行。一次有依据的修正后仍无新证据，就交付已完成部分及明确阻塞，结束本轮等待后续决定。原作业在运行时保留原jobId并报告等待，不另起计算。unknown/queued/running先核对原回执；绝不换key重复写入。

规划模板建议保留一张小表：`配件/数量｜关键尺寸及来源｜位置与连接｜批次｜本批验收点｜未确认项`。默认每批1–3个逻辑配件是调度建议，不是API上限，也不是把一次切孔、设颜色或重命名算成一个已完成配件。

复用同一对话的最新规划、已确认范围、当前工程与原回执；下一轮只续做未完成批次。人工编辑或工程重开后先核对当前身份和对象，不将历史bodyId用于写入。规划约1–2分钟交付、简单批次约2–3分钟出现成果或明确阻塞是体验目标，不是结束合法长作业的硬时限。
